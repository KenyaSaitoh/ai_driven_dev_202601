# 要件定義書 - Books Stock API（バックオフィス書籍在庫管理システム）

## 1. プロジェクト概要

### 1.1 プロジェクト名

Books Stock API - バックオフィス書籍在庫管理システム

### 1.2 目的

書店のバックオフィス業務において、書籍マスタ情報、在庫情報、価格改定などを管理するためのREST APIシステムを提供する。

### 1.3 対象ユーザー

* 書店の一般社員（ASSOCIATE）：書籍情報の参照、ワークフロー作成
* 書店のマネージャー（MANAGER）：自部署のワークフロー承認
* 書店のディレクター（DIRECTOR）：全部署のワークフロー承認

---

## 2. 機能要件（EARS記法）

### 2.1 認証・認可機能

#### 2.1.1 ログイン機能

FR-AUTH-001: WHEN 社員が有効な社員コードとパスワードを送信したとき、システムはJWT（JSON Web Token）を生成し、HttpOnly Cookieとしてレスポンスに設定しなければならない。

FR-AUTH-002: IF 社員コードまたはパスワードが正しくない場合、THEN システムは401 Unauthorizedエラーを返し、"メールアドレスまたはパスワードが正しくありません"というメッセージを表示しなければならない。

FR-AUTH-003: WHEN ログイン処理中、システムはパスワードをBCryptアルゴリズムで検証しなければならない。

FR-AUTH-004: WHERE 開発環境で平文パスワードが使用されている場合、システムは平文比較による認証をサポートしなければならない。

#### 2.1.2 ログアウト機能

FR-AUTH-005: WHEN 社員がログアウトリクエストを送信したとき、システムはJWT CookieのMaxAgeを0に設定して削除しなければならない。

#### 2.1.3 現在ログイン中のユーザー情報取得

FR-AUTH-006: WHEN 有効なJWT Cookieを持つリクエストが/api/auth/meに送信されたとき、システムは現在ログイン中の社員情報を返さなければならない。

FR-AUTH-007: IF JWT Cookieが設定されていない、または無効な場合、THEN システムは401 Unauthorizedエラーを返し、"認証が必要です"というメッセージを表示しなければならない。

---

### 2.2 書籍管理機能

#### 2.2.1 書籍一覧取得

FR-BOOK-001: WHEN 書籍一覧取得リクエストが送信されたとき、システムは論理削除されていない全書籍情報をカテゴリ、出版社、在庫情報とともに返さなければならない。

FR-BOOK-002: WHERE 書籍が1件も登録されていない場合、システムは空配列を返さなければならない。

#### 2.2.2 書籍詳細取得

FR-BOOK-003: WHEN 有効な書籍IDが指定されたとき、システムは指定された書籍の詳細情報をカテゴリ、出版社、在庫情報とともに返さなければならない。

FR-BOOK-004: WHEN 論理削除された書籍の詳細情報がリクエストされたとき、システムは当該書籍情報を返さなければならない（参照は可能）。

FR-BOOK-005: IF 指定された書籍IDが存在しない場合、THEN システムは404 Not Foundエラーを返し、"書籍が見つかりません"というメッセージを表示しなければならない。

#### 2.2.3 書籍検索機能

FR-BOOK-006: WHEN カテゴリIDが指定されたとき、システムは指定されたカテゴリに属する書籍一覧を返さなければならない。

FR-BOOK-007: WHEN キーワードが指定されたとき、システムは書籍名または著者名にキーワードを含む書籍一覧を部分一致で返さなければならない。

FR-BOOK-008: WHEN カテゴリIDとキーワードの両方が指定されたとき、システムはAND条件で書籍を検索しなければならない。

FR-BOOK-009: WHEN categoryId=0が指定されたとき、システムは全カテゴリから検索しなければならない。

FR-BOOK-010: WHERE 検索パラメータが指定されていない場合、システムは全書籍を返さなければならない。

FR-BOOK-011: システムはJPQL（静的クエリ）とCriteria API（動的クエリ）の両方による検索をサポートしなければならない。

FR-BOOK-012: WHEN N+1問題を防止するため、システムはJOIN FETCHを使用して1回のクエリで関連データを取得しなければならない。

---

### 2.3 カテゴリ管理機能

FR-CATEGORY-001: WHEN カテゴリ一覧取得リクエストが送信されたとき、システムは全カテゴリ情報を返さなければならない。

---

### 2.4 出版社管理機能

FR-PUBLISHER-001: WHEN 出版社一覧取得リクエストが送信されたとき、システムは全出版社情報を返さなければならない。

---

### 2.5 在庫管理機能

#### 2.5.1 在庫一覧取得

FR-STOCK-001: WHEN 在庫一覧取得リクエストが送信されたとき、システムは全在庫情報を返さなければならない。

#### 2.5.2 在庫情報取得

FR-STOCK-002: WHEN 有効な書籍IDが指定されたとき、システムは指定された書籍の在庫情報を返さなければならない。

FR-STOCK-003: IF 指定された書籍IDの在庫が存在しない場合、THEN システムは404 Not Foundエラーを返さなければならない。

#### 2.5.3 在庫更新機能

FR-STOCK-004: WHEN 在庫更新リクエストが送信されたとき、システムは楽観的ロック（@Version）を使用して在庫数を更新しなければならない。

FR-STOCK-005: WHEN 在庫が正常に更新されたとき、システムはversionフィールドを自動的にインクリメントしなければならない。

FR-STOCK-006: IF 在庫更新時にversionが一致しない場合（楽観的ロック競合）、THEN システムは409 Conflictエラーを返し、"他のユーザーが更新済みです。最新の在庫情報を確認してください。"というメッセージを表示しなければならない。

FR-STOCK-007: WHEN 複数ユーザーが同時に在庫を更新しようとしたとき、システムは楽観的ロックにより先に更新したユーザーのみ成功させ、後のユーザーにはエラーを返さなければならない。

---

### 2.6 ワークフロー管理機能

#### 2.6.1 ワークフロー作成

FR-WORKFLOW-001: システムは以下のワークフロータイプをサポートしなければならない：
* ADD_NEW_BOOK（新規書籍追加）
* REMOVE_BOOK（既存書籍削除）
* ADJUST_BOOK_PRICE（書籍価格改定）

FR-WORKFLOW-002: WHEN ワークフロー作成リクエストが送信されたとき、システムはワークフローレコードを作成し、初期状態をCREATED（作成済み）に設定しなければならない。

FR-WORKFLOW-003: WHEN ワークフローが作成されたとき、システムはcreatedByフィールドに作成者の社員IDを記録しなければならない。

#### 2.6.2 ワークフロー更新（一時保存）

FR-WORKFLOW-004: WHILE ワークフローの状態がCREATEDである間、システムはワークフロー内容の更新を許可しなければならない。

FR-WORKFLOW-005: WHILE ワークフローの状態がAPPLIED（申請中）またはAPPROVED（承認済み）である間、システムはワークフロー内容の更新を拒否しなければならない。

#### 2.6.3 ワークフロー申請

FR-WORKFLOW-006: WHEN ワークフロー申請リクエストが送信されたとき、システムはワークフローの状態をCREATEDからAPPLIEDに変更しなければならない。

FR-WORKFLOW-007: WHEN ワークフローが申請されたとき、システムはWORKFLOW_OPERATIONテーブルに操作履歴を記録しなければならない。

#### 2.6.4 ワークフロー承認

FR-WORKFLOW-008: WHEN 承認権限を持つ社員がワークフロー承認リクエストを送信したとき、システムはワークフローの状態をAPPLIEDからAPPROVEDに変更しなければならない。

FR-WORKFLOW-009: WHEN ワークフローが承認されたとき、システムは書籍マスタにワークフロー内容を反映しなければならない（ADD_NEW_BOOK: 新規書籍追加、REMOVE_BOOK: 書籍論理削除、ADJUST_BOOK_PRICE: 価格更新）。

FR-WORKFLOW-010: WHEN WORKFLOW_OPERATIONのINSERTと書籍マスタの更新は、システムは単一トランザクションで実行しなければならない。

FR-WORKFLOW-011: IF 承認処理中にエラーが発生した場合、THEN システムは全ての変更をロールバックしなければならない。

FR-WORKFLOW-012: IF 承認リクエストを送信した社員がASSOCIATE（一般社員）である場合、THEN システムは403 Forbiddenエラーを返し、"承認権限がありません"というメッセージを表示しなければならない。

FR-WORKFLOW-013: IF 承認リクエストを送信した社員がMANAGER（マネージャー）で、ワークフローの作成者と異なる部署に所属する場合、THEN システムは403 Forbiddenエラーを返し、"他部署のワークフローは承認できません"というメッセージを表示しなければならない。

FR-WORKFLOW-014: WHERE 承認リクエストを送信した社員がDIRECTOR（ディレクター）である場合、システムは全部署のワークフローを承認できるようにしなければならない。

#### 2.6.5 ワークフロー却下（差戻）

FR-WORKFLOW-015: WHEN 承認権限を持つ社員がワークフロー却下リクエストを送信したとき、システムはワークフローの状態をAPPLIEDからCREATEDに変更しなければならない。

FR-WORKFLOW-016: WHEN ワークフローが却下されたとき、システムはWORKFLOW_OPERATIONテーブルに却下の操作履歴を記録しなければならない。

#### 2.6.6 ワークフロー一覧取得

FR-WORKFLOW-017: WHEN ワークフロー一覧取得リクエストが送信されたとき、システムはクエリパラメータ（状態、タイプ）に基づいてフィルタリングしたワークフロー一覧を返さなければならない。

FR-WORKFLOW-018: WHEN ASSOCIATE（一般社員）がワークフロー一覧を取得しようとしたとき、システムは自分が作成したワークフローのみを返さなければならない。

FR-WORKFLOW-019: WHEN MANAGER（マネージャー）がワークフロー一覧を取得しようとしたとき、システムは自部署のワークフローのみを返さなければならない。

FR-WORKFLOW-020: WHEN DIRECTOR（ディレクター）がワークフロー一覧を取得しようとしたとき、システムは全部署のワークフローを返さなければならない。

#### 2.6.7 ワークフロー履歴取得

FR-WORKFLOW-021: WHEN ワークフロー履歴取得リクエストが送信されたとき、システムは指定されたワークフローIDのWORKFLOW_OPERATIONレコードを時系列順に返さなければならない。

## 3. 非機能要件（EARS記法）

### 3.1 性能要件

NFR-PERF-001: システムは、APIレスポンスタイムが通常時1秒以内となるように動作しなければならない。

NFR-PERF-002: システムは、最大50ユーザーの同時接続をサポートしなければならない。

NFR-PERF-003: WHEN 書籍一覧または検索APIが呼び出されたとき、システムはN+1問題を防止するためJOIN FETCHを使用して1回のSQLクエリで全データを取得しなければならない。

NFR-PERF-004: システムは、認証APIのレスポンスタイムが95パーセンタイルで500ms以内となるように動作しなければならない。

NFR-PERF-005: システムは、書籍APIのレスポンスタイムが95パーセンタイルで500ms以内となるように動作しなければならない。

NFR-PERF-006: システムは、カテゴリ・出版社APIのレスポンスタイムが95パーセンタイルで50ms以内となるように動作しなければならない。

NFR-PERF-007: システムは、在庫APIのレスポンスタイムが95パーセンタイルで200ms以内となるように動作しなければならない。

NFR-PERF-008: システムは、ワークフローAPIのレスポンスタイムが95パーセンタイルで1秒以内となるように動作しなければならない。

NFR-PERF-009: システムは、100リクエスト/秒のスループットを処理できなければならない。

NFR-PERF-010: システムは、書籍1000件を3秒以内に取得できなければならない。

### 3.2 セキュリティ要件

NFR-SEC-001: システムは、パスワードをBCryptアルゴリズムでハッシュ化して保存しなければならない。

NFR-SEC-002: システムは、JWTトークンを256ビット以上の秘密鍵で署名しなければならない。

NFR-SEC-003: システムは、JWTトークンの有効期限を24時間に設定しなければならない。

NFR-SEC-004: システムは、JWT CookieにHttpOnly属性を設定してXSS攻撃から保護しなければならない。

NFR-SEC-005: システムは、職務ランク（ASSOCIATE、MANAGER、DIRECTOR）による権限制御を実施しなければならない。

NFR-SEC-006: システムは、SQLインジェクション対策として、全クエリでJPQLの名前付きパラメータ（:parameterName形式）を使用しなければならない。

NFR-SEC-007: システムは、Criteria APIでコンパイル時型チェックを行い、タイプセーフなクエリを構築しなければならない。

NFR-SEC-008: IF ユーザー入力を直接SQL文字列に連結する実装がある場合、THEN システムはこれを拒否しなければならない。

---

### 3.3 可用性要件

NFR-AVAIL-001: システムは、稼働率99%以上を維持しなければならない。

NFR-AVAIL-002: システムは、トランザクション管理によりデータ整合性を保証しなければならない。

NFR-AVAIL-003: WHEN システム障害が発生したとき、システムは1時間以内に復旧しなければならない。

NFR-MAINT-001: システムは、SLF4Jによるログレベル管理を実施しなければならない。

NFR-MAINT-002: WHEN API呼び出しが成功したとき、システムはINFOレベルでログを出力しなければならない。

NFR-MAINT-003: WHEN ビジネスロジックエラーが発生したとき、システムはWARNレベルでログを出力しなければならない。

NFR-MAINT-004: WHEN システムエラーが発生したとき、システムはERRORレベルでスタックトレースとともにログを出力しなければならない。

NFR-MAINT-005: システムは、エラーメッセージを日本語で表示しなければならない。

NFR-MAINT-006: システムは、バージョン管理による楽観的ロックを実装しなければならない。

### 3.5 移植性要件

NFR-PORT-001: システムは、Jakarta EE 10準拠のアプリケーションサーバー（Payara Server 6.x以上）で動作しなければならない。

NFR-PORT-002: システムは、JPAによるデータベース抽象化を使用し、特定のデータベースに依存しない実装としなければならない。

### 3.6 データ整合性要件

NFR-DATA-001: システムは、BOOKテーブルの全レコードがCATEGORYテーブルに対応するcategoryIdを持つことを保証しなければならない。

NFR-DATA-002: システムは、BOOKテーブルの全レコードがPUBLISHERテーブルに対応するpublisherIdを持つことを保証しなければならない。

NFR-DATA-003: システムは、BOOKテーブルの全レコードがSTOCKテーブルに対応するレコード（1:1関係）を持つことを保証しなければならない。

NFR-DATA-004: システムは、WORKFLOWテーブルの全レコードがEMPLOYEEテーブルに対応するcreatedByおよびoperatedByを持つことを保証しなければならない。

## 4. 制約事項

### 4.1 技術制約

* Java 17以上を使用
* Jakarta EE 10準拠
* JAX-RS（RESTful Webサービス）を使用
* JPA（Jakarta Persistence API）によるデータアクセス
* HSQLDBをデータベースとして使用
* SLF4Jによるロギング

### 4.2 業務制約

BC-001: 書籍の物理削除は行わず、論理削除（deletedフラグ）で対応しなければならない。

BC-002: 論理削除された書籍は、システムは検索・一覧取得APIのレスポンスから除外しなければならない。

BC-003: 書籍詳細取得APIでは、システムは論理削除された書籍も参照可能としなければならない。

BC-004: ワークフローの操作履歴は、システムは全て保持しなければならない（監査目的）。

BC-005: 在庫更新時は、システムは楽観的ロックで排他制御を行わなければならない。

## 5. 受入基準

### 5.1 エンドツーエンドシナリオ

#### E2E-001: ログインから書籍検索まで

Given: ユーザーがシステムにアクセスする

When: 
1. POST /api/auth/login（ログイン）
2. GET /api/books（書籍一覧取得）
3. GET /api/books/1（書籍詳細取得）

Then: 
* 全ステップが成功する
* JWT Cookieが維持される

#### E2E-002: ワークフロー作成から承認まで

Given: ユーザーがログイン済みである

When: 
1. POST /api/workflows（ワークフロー作成）
2. POST /api/workflows/1/apply（ワークフロー申請）
3. POST /api/workflows/1/approve（ワークフロー承認）
4. GET /api/books（新規書籍確認）

Then: 
* 全ステップが成功する
* 新規書籍が反映される

#### E2E-003: 在庫更新フロー

Given: 在庫が存在する

When: 
1. GET /api/stocks/1（在庫取得）
2. PUT /api/stocks/1（在庫更新）
3. GET /api/books/1（在庫確認）

Then: 
* 全ステップが成功する
* 在庫数が正しく更新される

### 5.2 並行処理受入基準

#### CONC-001: 在庫更新時の楽観的ロック

Given: 2ユーザーが同時に在庫を更新しようとしている

When: 先に更新したユーザーが成功し、後から更新したユーザーが実行する

Then: 
* 先のユーザーは成功する
* 後のユーザーは409 Conflictエラーを受け取る
* データ整合性が確保される

#### CONC-002: 楽観的ロック競合後の再試行

Given: 409 Conflictエラーを受信した

When: 最新versionを取得して再更新する

Then: 再更新が成功する

## 6. 用語集

| 用語 | 説明 |
|------|------|
| JWT | JSON Web Token - 認証情報を含むトークン |
| BCrypt | パスワードハッシュ化アルゴリズム |
| 楽観的ロック | バージョン番号による並行制御 |
| HttpOnly Cookie | JavaScriptからアクセスできないCookie |
| JPQL | Java Persistence Query Language |
| Criteria API | タイプセーフな動的クエリAPI |
| 職務ランク | ASSOCIATE(一般社員)、MANAGER(マネージャー)、DIRECTOR(ディレクター) |
| ワークフロー状態 | CREATED(作成済み)、APPLIED(申請中)、APPROVED(承認済み) |
| ワークフロータイプ | ADD_NEW_BOOK、REMOVE_BOOK、ADJUST_BOOK_PRICE |
